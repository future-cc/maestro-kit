# 路由：什么时候用脚本、什么时候让 Claude 直接上手、什么时候排查、什么时候交给人

范围：**端到端（装好 App 在设备上点界面）**这一层。单元测试、接口测试不在这里。

## 一张表先选
| 情形 | 用什么 | 为什么 |
|---|---|---|
| 路径固定、每次发版都要确认，且已“连续 20 次全过”入库 | **脚本回归**：`e2e.sh --tags smoke` / 全量 | 快、可重复、有报告；人不用盯 |
| 新功能刚做完，界面和流程还没人走过，不知道元素叫什么 | **让 Claude 直接探索**（`maestro hierarchy` / Maestro MCP；小米/红米真机上它们每次都弹安装确认，改用 `adb uiautomator dump` + 截图，见 AGENTS.md 规则 11），走通后写成 flow，再走稳定性门槛 | 探索不需要写好脚本；但探索的结果**不是回归**，不能直接当通过依据 |
| 一次性问题：“这个页面现在长什么样”“这个按钮点了有没有反应” | **让 Claude 直接探索** | 写脚本不划算 |
| 回归跑红了 / 用例变得不稳定 | **排查**（见下一节） | 先搞清是 App、环境、用例还是设备的问题 |
| 要判断“好不好看、顺不顺、文案对不对”；**线上**的支付、转账、下单等真实写操作（测试环境 + 沙箱里的写操作可以脚本化）；验证码、设备校验、风控（后端放行测试账号之后可以脚本化）；真机才有的行为（推送、相机、生物识别）；第一次接触的新流程的整体体验 | **人看** | 脚本判断不了，或不该由脚本做 |

## 脚本回归怎么跑
```bash
bash .maestro/kit/e2e.sh --tags smoke --no-notify   # 先跑核心路径
bash .maestro/kit/e2e.sh --no-notify                 # 再跑全量
```
读 `summary.md`；**通过也要抽看最后一张截图**。多台设备并行用 `--devices a,b`（暂不能和 `--repeat` 同用）。

## Claude 直接探索时
- 只在**测试环境**；不碰正式环境、不做真实支付/转账/下单。
- 同一台设备同一时间只让一个东西操作（脚本在跑时不要同时探索）。
- 每走一步记下：看到什么、用了哪个 id/文字、预期是什么。发现问题先报告。
- 探索完要产出：步骤笔记，或一个草稿 flow。**草稿 flow 要走完 [WORKFLOW.md](WORKFLOW.md) 的第 3–5 步才算回归用例**。

## 排查：失败了先看这里
先读 `summary.md` 的“归类”，再**打开失败截图和失败时间点的日志**，不要只看退出码。

| 归类 | 通常是什么 | 先做什么 | 谁处理 |
|---|---|---|---|
| `element_not_found` | 页面没跳转、被弹窗/遮罩盖住、元素改名、元素在屏幕外 | 看失败截图；`maestro hierarchy` 看元素树 | 用例或开发（id 被改） |
| `assertion_failed` | 页面和预期不一致；或后端返回错误导致没渲染 | 看截图；看摘要里的“接口错误” | 先看是不是 App/后端的真问题 |
| `script_error` | JS 变量没传入、拼写错误 | 检查 `-e` / `e2e.env` | 用例 |
| `app_crash` | App 崩溃 | 看日志里的崩溃栈 | 开发（不是用例问题，别改用例） |
| `app_anr` | 被测 App 无响应（ANR），常见于冷启动超时；失败截图可能是别的 App（系统退回了上一个界面） | 看摘要里“ANR”那行的原因；`grep "ANR in" logcat.txt`；确认模拟器当时是否卡顿 | 开发 / 环境（不是用例问题） |
| `launch_failed` | App 没装、包名错、设备异常 | `--doctor`；确认已安装 | 环境 |
| `timeout` / 整体超时 | 网络慢、页面卡住 | 看截图和接口错误 | 环境或 App |
| `blocked_by_verification` | 被验证码/设备校验/风控拦住 | **停下，不绕过** | 后端对测试账号放行（见 [TEST_ENV_REQUIREMENTS.md](TEST_ENV_REQUIREMENTS.md)） |
| `unknown` | 未归类 | 读 `maestro_output.txt` 和截图 | 人 |
| **失败截图里不是被测 App 的页面** | App 没起来：启动超时（ANR，现在会归为 `app_anr`）、崩溃后系统退回了上一个 App | 看 `app_anr` / `app_crash` 的日志行；`grep "ANR in\|FATAL" logcat.txt`；看 App 进程是否启动 | 开发 / 环境 |

### “有时过有时不过”（不稳定）
1. 用 `e2e.sh <flow> --repeat 20 --no-notify` 量化到底多少次失败、失败原因是否相同（`<时间>_repeat/summary.md`）。
2. 常见根因（来自实测）：**冷启动落点/弹窗不固定**、等待不足（用固定秒数而不是等元素）、环境数据没重置、设备上有别的东西在操作。
3. **不要用 `--retry-failed` 掩盖**：重跑才通过的会被记为“不稳定”，不算通过；它只是帮你把偶发失败标出来。
4. 修好后重新跑 20 次，全过才恢复入库。

## 不适合自动测试的（不要硬写）
验证码、设备校验、短信、人脸、支付真实扣款、依赖当前时间的活动、需要真人判断的体验。这些交给人，并在 [ACCEPTANCE_CHECKLIST.md](ACCEPTANCE_CHECKLIST.md) 里写明“未覆盖”。
