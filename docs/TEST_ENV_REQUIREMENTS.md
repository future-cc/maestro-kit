# 给团队：自动测试需要什么样的测试环境

> **哪些必须先有**：第 1、2、5 节是**必须**（没有它们没法开始探索和写用例）；第 3 节（风控放行）涉及登录/短信/设备校验时必须；第 4 节（数据重置）涉及写数据时必须，没有时这些用例只能交给人验收，不能入回归库。第 6 节（设备）可以先用默认设置，后面再优化。

自动测试能不能稳，一半取决于脚本，**另一半取决于环境**。环境不稳时，同一条用例今天过明天不过，大家就不再信任测试结果。请团队帮忙准备下面这些（打勾确认）。

## 1. 独立、稳定的测试环境
- [ ] 与正式环境隔离的测试环境，**测试包只连它**（地址写在测试包里，或能用启动参数指定）
- [ ] 后端版本与被测的 App 版本对得上；发版、维护的时间提前告知，避开自动测试时段
- [ ] 测试机/模拟器所在网络能稳定访问它（不依赖个人 VPN、不会半夜断）
- [ ] 第三方依赖（短信、支付、地图、推送、广告等）在测试环境用**沙箱或模拟**，不触发真实扣款、真实短信
- [ ] 接口错误率低；出了问题有人能看到后端日志

## 2. 测试账号
- [ ] **专用的测试账号**，不与真人共用，不用真实用户数据
- [ ] 账号数量够：**同一个账号在多台设备同时登录可能互相踢线**，并行测试时每台设备需要各自的账号
- [ ] 账号**不会过期、不会被清理、密码不会被定期强制修改**；要改请同步通知
- [ ] 覆盖要测的角色/权限（如普通用户、付费用户、受限用户），每种至少一个
- [ ] 账号和密码**不写进代码仓库**：由测试负责人用安全方式给到各使用者，放在各机器本地的 `.maestro/e2e.env`（已被忽略，不会提交）

## 3. 对测试账号放行风控 / 验证（后端做，测试脚本不会绕过）
自动测试**不处理、也不绕过**验证码、设备校验、短信/人脸验证、反欺诈。如果这些会拦住测试账号，需要后端对**测试账号或测试设备**放行，例如：
- [ ] 测试账号免图形/滑块验证码，或使用固定的测试验证码
- [ ] 测试账号免“新设备/不信任设备”二次校验，或提供把测试设备加入白名单的办法
- [ ] 测试账号不会因为短时间内多次登录、多次失败而被冻结或限流
- [ ] 以上放行**只对测试环境、测试账号生效**，正式环境保持原样

## 4. 可重置的数据
自动测试会产生数据（下单、发帖、改资料）。要保证每次从**已知状态**开始：
- [ ] 有一键（脚本或接口）把测试账号的数据**恢复到约定的初始状态**，每次回归前执行
- [ ] 或者：用例每次创建自己的数据，并且在测试结束时能清理
- [ ] 测试账号的“初始状态”写成文档（余额、已有订单、已有收藏……），改动要通知
- [ ] 数据中**依赖当前日期/时间**的部分（活动期、赛事、优惠券）有固定的测试数据，不会“过了今天就没了”

## 5. 测试包
- [ ] 提供**测试包**（debug 或专门的测试渠道），包含 [DEV_CONVENTIONS.md](DEV_CONVENTIONS.md) 里的固定控件标识
- [ ] 测试包有开关**关掉启动弹窗、营销弹窗、新手引导**，冷启动落点确定
- [ ] 每次构建的包名、安装方式固定，产物路径固定（写进 `.maestro/e2e.config`）

## 6. 设备
- [ ] 固定一个或几个模拟器镜像（写明系统版本），存储空间够（至少几 GB 空闲）；真机另行评估
- [ ] 跑测试时设备不被别人同时操作；设备时区、语言固定
- [ ] 如果要多设备并行：设备数量、各自对应的账号已安排

## 7. 请团队回答的几个问题
1. 测试环境的负责人是谁？出问题找谁？
2. 测试账号谁管理？怎么申请新增？
3. 风控/验证会不会拦测试账号？谁负责放行？
4. 数据怎么重置？多久、谁来执行？
5. 测试环境有哪些时段不可用？
